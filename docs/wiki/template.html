Writing code mods for Ghostship

Ghostship mods are C source files packed into an .o2r archive. The game compiles them with TinyCC when it loads them, so a mod is plain text you can read, and the same archive works on every platform that runs code mods. This wiki covers how to build one and every function, structure and event a mod can use.

Your first mod

Start from workspace/template, inside a Ghostship checkout or the mod SDK zip. The SDK has the same layout and holds only what mods are built against: the headers, the mod tools and the template. A Ghostship checkout writes it with cmake --build build --target mod_sdk.

  1. Copy the template

    Copy workspace/template to workspace/my-mod and change project() in its CMakeLists.txt; the archive is named after it. Fill in manifest.json.

  2. Write the entry points 
    #include "mod.h"
#include "port/events/Events.h"
#include "game/level_update.h"

static void OnFrame(IEvent* event) {
    if (gMarioState->numCoins < 50) {
        gMarioState->numCoins = 50;
    }
}

MOD_INIT() {
    REGISTER_LISTENER(GameFrameUpdate, EVENT_PRIORITY_NORMAL, OnFrame);
}

MOD_EXIT() {
}
  3. Build it
    cmake -B build -S .
cmake --build build

    You need CMake 3.10 or newer, Python 3 and Pillow. The build fills output/ with the merged sources, build.gen, the stamped manifest.json and everything under assets/.

  4. Package and install it

    Zip the contents of output/ (not the folder itself) and rename the zip to my-mod.o2r. Copy it into Ghostship's mods/ folder and start the game. Compiler errors appear under Mods › General. Reload Scripts on the same page rebuilds every mod without restarting.

How the build packages a mod

The build merges each .c file in src/ with every Ghostship and libultraship header it includes into one self-contained file under output/dist/, and lists those files in build.gen. The game compiles exactly those files, so a mod never depends on headers being present on the player's machine. Everything from one source file ends up in one translation unit: mark helpers static so they don't collide with the game or other mods.

mod.h defines MOD_INIT and MOD_EXIT, routes malloc and free through the engine's allocator, and provides CALL_FUNC for calling into another mod.

Loading, reloading and cleanup

At startup the game mounts every enabled mod archive, compiles each mod's sources, then calls ModInit in dependency order. When a mod unloads, on exit or on Reload Scripts, the game calls its ModExit and then releases everything the mod registered:

  • content from the port/api headers, such as achievements, relay channels and stores;
  • event listeners, Mods menu pages and widgets, and GUI draw callbacks.

So MOD_EXIT is optional. Use it only to undo what the mod set up some other way, such as a game variable like gMarioState it changed directly.

The Mods menu

Mods › General lists every archive with a manifest and its state: loaded, failed to build (with the compiler's message), skipped (with the reason) or disabled. Each mod has an Enabled switch and a Priority. Mods with a higher priority are mounted later, so their files replace those of mods before them, and their code initializes later; dependencies always initialize first. Both settings take effect on the next start. A disabled mod isn't mounted at all.

Dependencies

A version range is a list of comparisons separated by spaces or commas: >=, >, <=, < and =. A version without an operator is a minimum. A mod whose dependency is missing, failed to build or falls outside the range is skipped with a notification, along with every mod that depends on it. Call into a dependency with CALL_FUNC(mod, func, ...) from mod.h.

Versions and compatibility

NumberNowGoes up whenEffect on mods
GS_API_VERSION2Something is added to the headersOlder mods keep loading. A mod that needs a newer API is skipped.
GS_CODE_VERSION2A change breaks mods built with older headersEvery mod must be rebuilt.

Definition structs only grow at the end. Each C_Register* macro, and C_AddWidget, passes sizeof the definition the mod was built with to the *Sized function behind it, so fields added in later versions read as zero for older mods. Always call the macro, not the *Sized function. The port/api headers keep their signatures across API versions; the game's own functions and structs, such as struct MarioState, may change with a new code version.

Achievements

Mods can add achievements next to the built-in ones. They show in the Achievements window with their icon and progress, and progress is kept in the save file. Use an id prefixed with the mod's name, such as "coinfloor.rich", and never reuse an id for a different achievement.

#include "port/api/achievements.h"

static const C_AchievementDef sRich = {
    .category = C_ACH_CATEGORY_EXTRAS,
    .name = "Deep Pockets",
    .icon = "extras.coinfloor-rich",
    .description = "Collect 500 coins.",
    .maxProgress = 500,
};

MOD_INIT() {
    C_RegisterAchievement("coinfloor.rich", &sRich);
}

// Later, whenever Mario picks up a coin:
//     C_AchievementProgress("coinfloor.rich", 1);
Keep ids stable. Progress is stored by id. Renaming an id loses every player's progress on it.

Save data and sounds

savedata.h keeps values in the save file being played, under "mods" in its save_<n>.json. They behave like the game's own progress: written when the game saves that file, erased and copied with it in the file select, and taken back to the last save after a game over. Prefix keys with the mod's name. Settings that belong to the player rather than one file go through cvar.h.

#include "port/api/savedata.h"

static void OnRedCoin(IEvent* event) {
    C_SaveDataSetInt("coinfloor.reds", C_SaveDataGetInt("coinfloor.reds", 0) + 1);
}

sound.h plays WAV, MP3 or FLAC files from the mod's archive, following the volume settings. C_ReplaceMusic plays a sound whenever the game starts a level sequence, and gives the game's music back when that sequence ends, fades or changes.

MOD_INIT() {
    const int theme = C_RegisterSound("music/castle.wav");
    C_ReplaceMusic(SEQ_LEVEL_INSIDE_CASTLE, theme, 0);
}

Assets: textures and models

C_ASSET(name, path) declares one of the game's own assets by its path in the game archive, to use as a Gfx*, texture or geo layout. The paths match the ones in the game's include/assets headers.

C_ASSET(sMarioHand, "actors/mario/geo/mario_geo_left_hand");

#asset copies a file next to the source into the mod archive when the mod is built, and turns the array into a reference to it that the game resolves at load time:

static const u8 sIcon[] = { #asset "textures/icon.png" };
static const u8 sBlob[] = { #asset "data/table.bin" };
SourceStored asNotes
.pngRGBA32 textureAlways full colour. To replace a texture of the game's that is smaller per texel, put its format in the file name (rgba16, ci8, ci4) so the renderer scales it to the original's size.
.binAs isRaw bytes, for data the mod reads itself.

Files under the mod's assets/ folder are copied into the archive as they are. A file at the same path as one of the game's replaces it, so a mod can also swap built-in textures, models and sounds without any code. Mods with a higher priority win.

On Windows a mod can only read or write a game variable whose declaration uses extern_s, which becomes __declspec(dllimport) when TinyCC builds a mod. Core globals such as gMarioState and the behavior scripts already do; functions don't need it. Include port/api/cvar.h instead of libultraship's console variable bridge. Unsigned mods load with a warning; archives can be signed with libultraship/tools/sign.py.

Online features with Satella

Satella is the online service Ghostship connects to when it starts, at wss://satella.net64.dev. It gives the game the keys trusted mods are signed with. Each install has a player key it proves to Satella on every connection, so every message says which player sent it (online.h). Mods go online through relay channels and rooms for messages between players, the player store for values kept for one player, and the channel store for values shared by everyone on a channel.

Player store, publicAnyone with the player's keyThe player, signed with their key4 KB per value

Permission comes first

A mod registers each channel with a name and one sentence about what it is for. The player is asked once per channel with an Allow / Deny prompt, and the answer is remembered in permissions.json. Until they allow it, sending and writing return FALSE. Reading the channel store and public player values needs no permission. Relay channels registered while mods load are asked about once the game is up; for the stores, call C_PlayerStoreRequestPermission or C_ChannelStoreRequestPermission when the player first uses the feature. permissions.h gives a mod the same prompt for its own needs.

A chat channel

#include "mod.h"
#include "port/api/relay.h"
#include <string.h>

static void OnChat(const char* channel_id, const char* sender, const char* data, uint32_t size) {
    // Runs on the game thread for every message; sender is the key of the player who sent it.
}

static C_RelayChannelDef sChat = {
    .mod_name = "Castle Chat",
    .description = "Sends what you type to other players in castle chat.",
    .on_message = OnChat,
    .mod_version = "1.0",
};

void SayHello(void) {
    const char* text = "Let's-a go!";
    if (!C_RelaySend("castle.chat", text, strlen(text))) {
        // Not allowed yet, or Satella isn't connected.
    }
}

MOD_INIT() {
    C_RegisterRelayChannel("castle.chat", &sChat);
}

Reading stored values

static void OnBest(const char* key, const char* data, uint32_t size) {
    if (data == NULL) {
        return; // nothing stored yet
    }
}

static C_PlayerStoreDef sTimes = {
    .mod_name = "Speedrun Times",
    .description = "Keeps your best time on each course.",
};

MOD_INIT() {
    C_RegisterPlayerStore("speedrun.times", &sTimes);
    C_PlayerStoreGet(NULL, "speedrun.times", C_PLAYER_STORE_PUBLIC, "bob", OnBest);
}

Reads answer later, through the callback. Every callback runs on the game thread, as the mod that asked, and is skipped if the mod has unloaded by then. Writes and deletes are sent without waiting for an answer.

Where it works

Satella is in every build that runs code mods, and players can turn it off under Dev Tools › General › Enable Satella. Without it these calls return FALSE or a denied permission and nothing arrives, so a mod should treat online features as optional. Relay channels are kept apart by game version, and by mod_version when the mod gives one, so players on different versions don't receive each other's messages.

Listening to events

The game fires events at the points mods are likely to care about. A listener receives an IEvent* to cast to the event's own struct.

static ListenerID sAction;

static void OnSetAction(IEvent* event) {
    PlayerSetAction* ev = (PlayerSetAction*)event;
    if (ev->action == ACT_LONG_JUMP) {
        event->Cancelled = true;   // no more long jumps
    }
}

MOD_INIT() {
    sAction = REGISTER_LISTENER(PlayerSetAction, EVENT_PRIORITY_NORMAL, OnSetAction);
}
KindWhat a listener can do
cancellableSet event->Cancelled = true to stop the game's default behaviour. Each event says what cancelling does.
Pointer fieldsFields typed as pointers, like s8* background, let a listener change what the game uses by writing through them, without cancelling.
PriorityListeners run from EVENT_PRIORITY_HIGH to EVENT_PRIORITY_LOW. Later listeners still run after a cancel and can check event->Cancelled.

UNREGISTER_LISTENER(Event, id) removes a listener while the mod runs; listeners still registered when it unloads are removed for it. Most events fire on the game thread; the few that fire on the audio thread say so, and their listeners must not touch game state.
